# DSCODE 0.7.51

The terminal upgrades to Harness rc.3, reduces file and desktop observation overhead, and adds explicit unattended-server and private Linux desktop modes.

## Runtime and model compatibility

The terminal/server pins Harness `0.2.1-rc.3`. The official DeepSeek API-key route follows the authenticated model listing and its declared capabilities while preserving DSCODE's Ultra effort. Initial listing failure falls back to the bundled catalog; failed refreshes retain the last successful listing. Custom endpoints and explicit catalogs keep their configured models. The browser MCP image adapter accepts the verified rc.3 implementation without weakening its bounded base64 checks.

Remote clients and servers must use the same Harness version. The separate Desktop plugin remains on `0.2.0-rc.2` and does not gain the terminal's file-tool patches or Linux desktop backend.

## Smaller file and shell operations

`edit_many` applies a validated batch with one atomic write, retaining read-before-edit, stale-version and sandbox checks. Range reads stop after their requested window and use a bounded session/file-version cache. Exact line totals are returned only at EOF, and the TUI can display partial windows without a total. Batch editing still reads and rewrites the complete file once; caches do not persist across resume.

Persistent Bash saves large captured output before inline truncation and returns a path for later reads/searches, including failure and timeout output. Capture remains bounded at 4 MiB; larger complete logs require explicit redirection. PowerShell and `shell_retry` limits are unchanged.

## Unattended servers and Linux desktops

`dscode server --yolo` preauthorizes file/shell, browser site/developer and application access, and answers sensitive-action approvals with an audit trail. It applies to resumed and delegated agents without saving elevated session policies or browser grants. Managed service installation preserves the flag. Ordinary Hosts keep their existing policy. Authentication, cancellation, stale-target checks and OS permissions still apply.

Linux Computer Use uses a persistent AT-SPI helper, explicit screenshots and incremental observation output. Name/role/window filters and observation-bound subtrees reduce returned data and traversal. Mutation tools can check an `expect` predicate; `computer_wait_for` uses accessibility events with bounded fallback reads. A timeout never automatically replays an uncertain action.

Desktop leases serialize input across cooperating Hosts and agents in the same user/display/filesystem namespace. `computer_control` reserves a bounded sequence; `/computer pause` revokes control and `/computer resume` permits new leases. Logind-reported locked/inactive sessions refuse input, while unknown state remains explicitly unknown.

`dscode server --yolo --desktop` starts an authenticated private Xvfb/Openbox display and session bus. `dscode desktop exec -- COMMAND` launches an application there. The supervisor recovers display/window-manager failures and invalidates observations; it does not replay tasks or restart application processes. This separates displays, not OS accounts or filesystem permissions. The desktop remains running after the server stops until explicitly stopped.

## Experimental Wayland support

`/computer connect` requests a RemoteDesktop/ScreenCast session; `connect-keyboard` requests keyboard access only. Stream screenshots carry logical dimensions and a stream ID for explicit stream-local pointer coordinates. Pointer mapping requires full desktop application access. OS consent remains required even in YOLO mode. No root, uinput or XWayland-input fallback is used.

PipeWire capture keeps only the latest frame and rejects cached data after two seconds without a fresh frame. A fully static desktop can therefore need a screen update before another capture. Portal revocation and helper/session changes invalidate old observations.

Native GNOME/KDE visual pointer placement, authorization dialogs, mixed-DPI/multiple monitors and real logind transitions have not been qualified. The Docker environment lacks a DRM render device; its KWin screenshots were not accepted as successful desktop qualification. Real PipeWire test-source capture and Portal contract tests are narrower evidence.

## Validation

Before release preparation, 1,338 unit/component cases, all sixteen integration verifiers, package checks, lint and documentation checks passed. The macOS ARM64 standalone candidate passed private Node/native imports, PTY, Host start/stop, cold configuration, installation, relocation, whole-package updating and settings preservation. Real Linux helper/Host/private-desktop fixtures passed, as did six scripted application tasks across GTK, Qt, Chromium, Electron, Mousepad and Thunar. Chromium/Electron cases verify accessible buttons, not HTML text editing. A real synthetic PipeWire source verified nonblank PNG output and bounded stale-frame reuse.

The large GTK fixture reduced one-control traversal from 310 nodes to 1 and backend JSON from approximately 94 KB to 1.1 KB; five-sample read P95 fell from approximately 94 ms to 10 ms on the local ARM64 fixture. These are scripted fixture measurements, not model-token savings or production latency guarantees. Release CI runs the full gate and qualifies all four platform archives before publication. Live provider inference, native macOS permission UI, deployed Linux login recovery and the Wayland paths listed above remain outside this qualification.
