# DSCODE 0.7.50

Remote servers gain managed user services and diagnostics, while session writes recover after restarts and protect retries, interrupts and deletion against competing clients.

## Running and inspecting a server

`dscode server install/start/stop/restart/uninstall/status/logs/connect` manages a macOS LaunchAgent or Linux systemd user service. Start and status verify the authenticated TCP endpoint and its managed identity. Stop, restart and uninstall refuse attached clients or running turns unless explicitly forced. Unit definitions and ordinary logs omit the bearer token; `server connect` explicitly prints the connection command.

Standalone updates also refuse running turns, pause an idle managed server before replacing its installation and restore it after success or failure. The installation gates are released before the service resumes. A foreground server announces readiness only after its authenticated endpoint responds.

`dscode runtime status <alias>` and `dscode runtime doctor <alias>` support JSON output and failure exit codes. Doctor inspects the server folder and mounted services without running a model or testing provider credentials. `dscode config --alias <name>` preserves omitted address, token and folder fields; `--clear-cwd` explicitly clears a folder override. The remote footer keeps the alias, connection state and session folder visible within the terminal's available width.

These are user services, subject to the OS user's service and login policies. TCP remains token-authenticated but unencrypted: use a trusted network, VPN or SSH tunnel. Browser-login forwarding and remote downloads are unchanged.

## Connection compatibility and recovery

Servers now declare a protocol revision, pinned Harness version and optional capabilities. Application versions may differ when both protocol revision and Harness version match. This release declares revision 2 for structured session mutation errors; legacy servers without a declaration still require exactly equal application versions. Upgrade both client and server when moving from 0.7.49.

Transient network failures reconnect. Token refusal and incompatible protocol contracts stop retries and further client requests. Reconnection checks compatibility before reporting recovery or replaying approvals, and disconnection withdraws open approval prompts. History recovery validates contiguous sequences and page progress, cancels pending work when switching sessions and closes failed initial follows. Session-domain errors are reported instead of being mistaken for network outages.

## Session writes and storage ownership

Delivery and queue editing now restore cold Agents through the upstream Session Controller. Upstream `session/follow` reads history without restoring an Agent; after a server restart, following alone previously left the first write unable to find a live Agent.

Delivery accepts an optional request ID. Repeating an accepted request returns its existing result, while reusing the ID with different content, mode or context fails with a structured conflict. Receipts survive queue edits, cancellation and persisted restarts, and writes with request IDs flush before acknowledgment. The terminal assigns request IDs to submissions. It does not automatically resend uncertain writes: typing a new submission creates a new ID. Deduplication depends on retained session logs and successful persistence; it cannot provide exactly-once delivery after disk loss, external rollback or a storage-free restart.

Interrupts can include the observed turn sequence so a delayed interrupt cannot cancel a newer turn. Successful queue edits, interrupts and renames flush before acknowledgment. Session-extension arguments are validated before mutation, and missing-session, ownership and busy failures carry structured codes.

Deletion acquires storage write ownership for every observed subtree member before removing logs and retains lock inodes. Cancellation before removal releases acquired handles; once removal begins it completes the planned work despite a disconnected caller. This is not a multi-session transaction: an I/O failure can leave a partially removed subtree, and forks created after the observed snapshot are not globally serialized with it.

## Verification

On macOS, the complete `npm run check` gate passed: lint, both TypeScript configurations, 1,304 unit/component tests with 80.08% first-party `.mjs` line coverage, all integration verifiers, package checks and 63 offline evaluations. Documentation checks and the manifest/tag version check also passed. Real Host, remote-runtime, managed-service and three-mode terminal verifiers passed using temporary state and fixture models. Host verification covers concurrent explicit-ID creation, cold session recovery and durable delivery deduplication across restart. History fixtures exercise multi-page catch-up, duplicate events, invalid paging and cancellation. Deletion cases use two real JSONL backend instances sharing storage to exercise ownership and concurrent deletion.

The managed-service verifier uses real Host processes with an injected process manager; it does not register a service with the OS. Generated macOS property lists pass `plutil` validation. Live launchd/systemd registration, login/logout behavior, an OS-managed service upgrading through a downloaded release, multi-machine NAT/VPN failures and live provider calls have no new automated or live case in this change. Platform package qualification is performed by the release workflow before terminal publication.
